# FireGuard 接处警与救援站闭环

## Goal

在现有重点单位监测 Demo 上增加独立的消防接处警闭环：设备信号先进入核实任务，只有人工确认为真实警情后才能创建警情；总队/支队可调派辖区内虚拟消防救援站，救援站可反馈签收、出动、到场和现场首报，两个工作台通过 PostgreSQL 与 SSE 实时同步。

## Acceptance Criteria

1. 每条合成设备火警信号对应一个核实任务，状态只能从“待核实”进入“已确认”或“已排除”；排除后不创建警情。同一终态的重复请求幂等返回原结果，尝试改为另一终态返回 `409` 且不写入警情。
2. 用户执行“确认警情”后，系统创建一条关联企业和原设备事件的合成警情，初始状态为“待调派”；同一设备事件最多创建一条警情，重复确认返回原警情而不重复写入。
3. 总队只能把“待调派”警情调派给覆盖企业所在辖区且状态为“可调派”的虚拟消防救援站；高新区至少提供两个可选虚拟站点。服务端先检查该警情是否已有调派单：同站点重复请求幂等返回原单，不同站点返回 `409`；仅在没有原调派单时，再依次校验辖区（不匹配返回 `422`）和站点状态（非“可调派”返回 `409`），失败时不得创建调派单。
4. 调派单状态只能按“已下达 → 已签收 → 已出动 → 已到场”顺序更新。非法跳转返回 `409`，不存在或缺少字段返回相应 `4xx`，且不得改变原状态。
5. 救援站到场后可提交一条现场首报，必填“现场情况”（1–300 字）和“人员情况”（未知、无被困风险、存在风险）。到场前提交返回 `409`；同内容重复提交幂等返回原首报，不同内容重复提交返回 `409`，均不得重复写时间轴。
6. 警情创建、调派、状态变化和现场首报必须写入 PostgreSQL 时间轴，并通过 SSE 推送。活动连接下另一端应在 2 秒内更新且无需刷新；断线重连后从 PostgreSQL 恢复最新状态，SSE 只用于通知。
7. 总队页面显示核实队列、合成警情队列、辖区站点、调派动作、处置时间轴和虚拟力量状态；救援站页面突出当前任务及签收、出动、到场、首报按钮。站点初始为“可调派”；调派下达后为“待签收”；站端签收后为“已受领”；车辆出动后为“出动中”；到场后为“现场处置”。
8. 首战提示只使用 PostgreSQL 中的合成现场档案（地址、危险源、入口、水源、消防设施），每条建议显示来源字段；缺失数据明确显示“未知”，不得补写。
9. 页面和时间线明确标注“模拟角色、合成警情、未连接 119”；所有新增成功 JSON 响应和 SSE 数据事件顶层包含 `is_simulation: true` 和 `external_system: "none"`，标准错误响应与 SSE keepalive 注释除外。首战提示固定标注“仅供辅助，不替代现场指挥”。

## Failure Conditions

- 设备报警未经人工确认即进入警情列表。
- 核实任务、调派单状态可跳级，或重复流转造成冲突记录。
- 页面显示成功但数据库没有对应记录。
- SSE 断开后页面不再恢复数据库真实状态。

## Boundaries

- 本轮只使用虚拟企业、虚拟警情和虚拟救援站。
- 不连接真实 119、消防通信、车辆定位、道路导航或人员系统。
- 不实现自动调派、自动决策或真实作战指令。
- 设备信号确认标准、辖区匹配、调派权限、状态术语、站端首报字段和新能源首战提示内容需要真实消防专家校验后才能用于生产。

## Non-Goals

- 不实现账号、RBAC、多租户和生产审计。
- 不实现“处置中、结束、归档”、GIS 路径计算、视频会商、跨区域增援和复杂 ICS 组织结构。
- 不新增模型服务；AI 首战提示先用可解释的规则模板生成。
